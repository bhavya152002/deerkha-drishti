Check before that first commit

standalone/env holds a live Telegram token and database password. It is gitignored, but confirm nothing sensitive is staged — git history is permanent.

git add -A --dry-run | sed "s/^add '//;s/'$//" \
  | grep -iE "(^|/)\.env$|standalone/env|\.engine$|\.mp3$"
# expect NO output

The sed is not decoration: git add --dry-run prints add '.env', quotes included, so a pattern anchored with $ silently matches nothing and the check passes while a secret is staged.

01

VPS base

~15 min

Create the VPS and a working user

VPS, as root

Order the box with Ubuntu 24.04 in the Mumbai region, then:

adduser --gecos "" deerkha-admin
usermod -aG sudo deerkha-admin
install -d -m 700 -o deerkha-admin -g deerkha-admin /home/deerkha-admin/.ssh

From your laptop, install your key, then confirm key login works before the installer disables password auth:

# laptop
ssh-copy-id deerkha-admin@<vps-ip>
ssh deerkha-admin@<vps-ip> 'echo key login works'

Join Tailscale and take a stable name

VPS

Do this before the installer — it binds Postgres to the tailnet address only if Tailscale is already up.

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale ip -4          # note this address

In the Tailscale admin console, rename this machine to deerkha-vps and make sure MagicDNS is enabled. Using the name rather than the IP means you can move the server later without editing every Jetson.

Clone the repository

VPS

The installer reads server/requirements.txt and server/schema.sql from the clone, so it must be present first.

sudo apt-get update -qq && sudo apt-get install -y -qq git
git clone -b v1.0.1 https://<pat>@github.com/bhavya152002/deerkha-drishti.git ~/deerkha
cd ~/deerkha && git describe --tags && ls server/schema.sql

Both of those must succeed before you continue: git describe should print v1.0.1, and schema.sql must exist. If the repository is still public, drop the <pat>@ — no credential is needed.

Always clone the TAG, never the default branch

A bare git clone checks out whatever the host has set as the default branch, which is not necessarily the one carrying this release — on the GitLab mirror it is not. The first symptom is the installer reporting schema.sql not found, after it has already built Postgres. -b v1.0.1 pins the exact reviewed commit, which is also what makes a deploy reproducible and a rollback meaningful.

Once the repository is private: a read-only credential

GitHub does not accept your account password over HTTPS. Create a fine-grained personal access token — Settings → Developer settings → Personal access tokens → Fine-grained — with Repository access limited to this one repository and Contents: Read-only. Nothing else. Use it in place of <pat> above.

The token then lives in ~/deerkha/.git/config on the VPS. It is read-only and single-repo, so that is a reasonable trade — but to keep it off disk, run git remote set-url origin https://github.com/bhavya152002/deerkha-drishti.git once the clone finishes. Re-supply the token the next time you pull.

The alternative, if you would rather have no token at all: add a deploy key (repo → Settings → Deploy keys) using a keypair generated on the VPS with ssh-keygen -t ed25519, and clone the git@github.com: URL instead. Read-only by default, and revocable without touching your account.

Run the installer

~10 min, unattended

One command builds the whole server

VPS 
sudo bash ~/deerkha/deploy/server/install-server.sh

It is idempotent — safe to re-run after fixing anything. What it does:

StepWhy it matters
Sets timezone to UTC before installing Postgres The edge sends naive UTC timestamps. A cluster created under Asia/Kolkata puts every detection 5h30m ahead of the rest of the history — invisible for weeks.
Installs Postgres, nginx, certbot—
Tunes Postgres for 2 vCPU / 8 GB / NVMeshared_buffers=2GB, random_page_cost=1.1, timezone='UTC' pinned.
Creates database deerkha and two roles deerkha for the app; deerkha_edge which can only INSERT into detections. A stolen field box cannot read or damage anything.
Applies schema.sqlAll cfg_* tables plus detections.

03

Admin login

do not skip

Set the admin username and password

VPS
The installer wrote CHANGE_ME, and the app will boot with it

There is no users table yet — login is a single username/password pair read straight from the environment and compared with hmac.compare_digest. Whatever you put in this file is the login. If you leave it, your password is literally CHANGE_ME.

Generate a session secret, then edit the file:

python3 -c "import secrets; print(secrets.token_urlsafe(48))"
sudo nano /etc/deerkha-server/server.env

Set these three. DATABASE_URL is already filled in.

SESSION_SECRET=<paste the generated string>
ADMIN_USERNAME=<choose>
ADMIN_PASSWORD=<choose a strong one>
All four are required

DATABASE_URL, SESSION_SECRET, ADMIN_USERNAME, ADMIN_PASSWORD — the app raises at import and refuses to start if any is missing. That is deliberate: a server that will not start is loud, one with a guessable admin cookie is silent. Changing SESSION_SECRET later logs everyone out.

04

Deploy the code

~5 min

Put the release in place and start the service

VPS

Same immutable-release pattern as the Jetsons: code lands in a per-tag directory and current is a symlink you can flip back.

TAG=v1.0.0
sudo install -d -o deerkha -g deerkha /opt/deerkha-server/releases/$TAG
sudo cp -a ~/deerkha/server/. /opt/deerkha-server/releases/$TAG/
sudo chown -R deerkha:deerkha /opt/deerkha-server/releases/$TAG
sudo ln -sfn /opt/deerkha-server/releases/$TAG /opt/deerkha-server/current.new
sudo mv -Tf /opt/deerkha-server/current.new /opt/deerkha-server/current

sudo systemctl enable --now deerkha-server
sudo systemctl status deerkha-server --no-pager

Confirm it can actually reach the database — this endpoint returns 503 if it can't:

curl -s localhost:8000/healthz
# expect: {"ok":true,"db":"ok"}
If it will not start

Almost always a missing value in server.env. The traceback names the variable:

sudo journalctl -u deerkha-server -n 40 --no-pager

05

Domain and HTTPS

~10 min + DNS propagation

Point two names at the VPS

your domain registrar / DNS
RecordNameValueServes
AadminVPS public IPFull dashboard — your team
An A record, not a CNAME — and do not add app yet

It must point straight at the VPS IP. Routing it through a CDN breaks two things: the ACME challenge cannot reach your nginx, and the MJPEG live streams are long-lived unbuffered responses that a CDN will stall.

app waits until the client dashboard exists. Both hostnames proxy to the same application, so publishing app today exposes the admin login to the internet behind a single shared password.

Wait for it to resolve before running certbot. Let's Encrypt rate-limits failed validations, and burning them against a record that has not propagated costs you an hour.

dig +short admin.<domain>
# must print the VPS IP. Empty = not propagated, or the record is missing.

Enable the vhost and get certificates

VPS

Three stages, in this order. The real config declares listen 443 ssl and so needs a certificate that does not exist yet; the bootstrap vhost exists to break that circle.

# 1. HTTP-only vhost, so nginx starts and can answer the ACME challenge
sudo install -m 644 ~/deerkha/deploy/server/nginx-deerkha-bootstrap.conf \
     /etc/nginx/sites-available/deerkha
sudo ln -sf /etc/nginx/sites-available/deerkha /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 2. issue the certificate WITHOUT letting certbot rewrite nginx
sudo certbot certonly --webroot -w /var/www/html -d admin.<domain>

# 3. swap in the real config, cert paths already correct
sudo install -m 644 ~/deerkha/deploy/server/nginx-deerkha.conf \
     /etc/nginx/sites-available/deerkha
sudo nginx -t && sudo systemctl reload nginx
Why certonly rather than --nginx

--nginx edits your configuration in place. The reviewed config in git would stop being the config that runs, and the security headers, the path denies and the unbuffered MJPEG location would not survive a later regeneration. certonly --webroot only writes certificates and never touches nginx, so git stays the source of truth.

Renewal keeps working: certbot's timer renews the certificate in place, and nginx picks it up on reload. Nothing in the config needs to change at renewal.

Verify what is and isn't reachable

Run all four — the last two must fail

The app binds 0.0.0.0 so Jetsons can reach it over Tailscale. ufw is the only thing keeping port 8000 off the public internet.

# must SUCCEED
curl -sI https://admin.<domain>/login | head -1
curl -s  https://admin.<domain>/healthz

# must TIME OUT (not connect, not 404)
curl --connect-timeout 5 http://<vps-public-ip>:8000/healthz
curl --connect-timeout 5 http://<vps-public-ip>:5432

Now open https://admin.<domain> and log in with the credentials from step 03.

06

First device record

~5 min

Seed the device and capture its token

VPS

Create it with seed.py rather than the dashboard: seeding fills in class settings, CLIP prompts and deterrence targets, whereas a dashboard-created device currently comes up with none of those — meaning detection is effectively off.

cd /opt/deerkha-server/current
sudo -u deerkha /opt/deerkha-server/venv/bin/python seed.py \
    --device-id jetson-forest-01 --name "Forest Site 01"
Copy the device token it prints — now

It is shown once. If you lose it, rotate from the device page and use the new one. This goes into that Jetson's device.env in step 09.

Verify the assembled config matches the source constants:

sudo -u deerkha /opt/deerkha-server/venv/bin/python verify_seed.py \
    --device-id jetson-forest-01

The --device-id must exactly match JETSON_DEVICE_ID on the box, or config polling 404s and the Jetson runs on its fallback — which has no cameras.

07

Jetson hardware and OS

per box

Flash JetPack and mount the NVMe

Jetson
Never record to the eMMC or an SD card

Eight concurrent writers exceed a card's sustained throughput, and the write volume kills it inside a year. Recording must land on the NVMe at /mnt/data.

Use the same JetPack version on every box — the one-artifact model and the shared TensorRT engines both depend on it.

lsblk                                  # find the NVMe, e.g. nvme0n1
sudo mkfs.ext4 /dev/nvme0n1
sudo mkdir -p /mnt/data
echo "/dev/nvme0n1 /mnt/data ext4 defaults,noatime 0 2" | sudo tee -a /etc/fstab
sudo mount -a
df -h /mnt/data                        # confirm ~465 GB
465 GB does not hold 3 days at 8 cameras

Budget about 400 GB usable — the cleanup rule holds back 10% free, and JetPack plus /opt/deerkha take 25–30 GB if this is also the boot device. At the modelled ~21 GB per camera per day that is ~2.4 days across 8 cameras, and closer to 1.5 days on a night when motion runs continuously.

The cheapest fix is not in our code: drop the camera's own H.265 bitrate from 3 Mbps to 2 Mbps and a full 3-day window fits, with little visible loss at 1080p. Set cleanup_days_to_keep to 2 on the dashboard until you have measured a real week — every figure here is modelled, not observed.

Join Tailscale and verify both directions

Jetson 
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale status | grep deerkha-vps    # want 'direct', not 'relay'
getent hosts deerkha-vps               # MagicDNS must resolve
curl -s http://deerkha-vps:8000/healthz
If the name does not resolve but the IP pings

On stock JetPack, tailscaled sometimes cannot take over /etc/resolv.conf under NetworkManager. Either fix DNS, or add a line to /etc/hosts: <vps-tailscale-ip> deerkha-vps. Ugly but reliable, and it keeps the hostname in device.env so the server can still move.

08

Build the TensorRT engines

once for the whole fleet

Build on one reference box, ship to all

Engines are not portable across GPU architecture

Anything built for the old Jetson Nano (Maxwell) will not load on Orin (Ampere). A failed load raises at import — which is exactly why the systemd unit sets StartLimitIntervalSec=0. Without it, systemd gives up permanently after five restarts and the box is dark until someone drives to it.

Build on one Orin of the same SKU and JetPack, then place the files on your laptop. They are gitignored and shipped separately from the code.

# laptop, in the repo
models/rfdetr_fp16.engine
models/mobileclip2_s2_image_fp16.engine
models/pt/mobileclip2_s2.pt
sounds/*.mp3                # deterrence audio

Because every box is the same SKU and JetPack, one build serves the entire fleet.

09

Provision the box

~10 min per box

Run the provisioner

laptop → Jetson

Both files must be copied — the script installs the unit from /tmp.

scp deploy/deerkha-drishti.service deploy/provision.sh \
    <user>@<jetson-tailscale-ip>:/tmp/
ssh <user>@<jetson-tailscale-ip> 'sudo bash /tmp/provision.sh'

It creates the deerkha service user with the right groups (video,render for NVDEC/GPU, dialout for the USB relay, audio for deterrence), the /opt/deerkha layout, a venv with --system-site-packages (so tensorrt, cv2, torch and gi come from JetPack), logrotate, a narrowly scoped sudoers entry, and the systemd unit.

Write the box's identity

Jetson

This is the only per-device file. Cameras, RTSP credentials, ROI, classes, prompts, thresholds, retention and the Telegram bot token and chat id all come from the server. A deploy never touches it.

sudo nano /etc/deerkha/device.env
JETSON_DEVICE_ID=jetson-forest-01
CONFIG_API_TOKEN=<device token from step 06>
CONFIG_SERVER_URL=http://deerkha-vps:8000

# Until alerts route through the server, the edge still writes to Postgres
# directly. Use the deerkha_edge credential from step 02 -- it can only
# INSERT into detections.
DATABASE_URL=<from /etc/deerkha-server/edge-db-credential.txt>

# Telegram is configured on the DASHBOARD, not here. Leave these out.
Only DATABASE_URL causes a crash-loop if missing

DATABASE_URL is required — the pipeline raises at import without it. The Telegram values are deliberately not required: a fresh box receives them in its first config poll, and hard-requiring them would kill the process before it could ever poll. A box with no token starts normally, logs its alerts, and begins sending as soon as the server delivers one.

Set the Telegram token once, for the whole fleet

Dashboard → any device → Global settings → Telegram bot token — fleet-wide. Every box picks it up on its next poll (~30 s), with no restart and no SSH. Set Telegram chat id per device to route each site to its own group — or give several devices the same chat id to pool them into one. The per-device bot token override just below it is only for a site running its own bot; leave it blank otherwise.

The token is never displayed again after saving, and it is redacted from the preview-config view and from the audit log. It is written to each box's config cache at /var/lib/deerkha/config_cache.json (mode 0600) — so this makes rotation easy, it does not make a stolen box harmless.

10

Ship the code

~5 min

Add the box to the fleet inventory

laptop

One line per box: device id, Tailscale IP, ssh user. The first uncommented line is the canary — put a box you can physically reach there.

nano deploy/fleet.txt
# jetson-forest-01   100.x.y.z    deerkha

Deploys use ssh with BatchMode=yes, so key auth to the deerkha user must already work without a prompt.

Push the engines, then deploy

laptop 
./deploy/push-models.sh jetson-forest-01
./deploy/deploy.sh v1.0.0 --only jetson-forest-01
./deploy/deploy.sh --status

deploy.sh stages the tag into /opt/deerkha/releases/<tag>, flips the current symlink atomically, restarts the unit, then waits for the box to prove itself healthy: service active, restart count not climbing, and a fresh HEARTBEAT line in the log. If that fails it rolls the box back to the previous release and halts the rollout.

Working on the box instead of over ssh? Use local-deploy.sh

If you administer the Jetson directly — remote desktop, console, or a keyboard in the field — run the deployment on the box and skip ssh entirely. Same staging, same atomic symlink swap, same health gate, same auto-rollback.

# on the Jetson, once: a clone to deploy from
git clone https://github.com/bhavya152002/deerkha-drishti.git ~/deerkha-src

# engines go straight into place (no push-models.sh needed)
sudo install -d -o deerkha -g deerkha /opt/deerkha/models/pt
sudo cp rfdetr_fp16.engine mobileclip2_s2_image_fp16.engine /opt/deerkha/models/
sudo cp mobileclip2_s2.pt /opt/deerkha/models/pt/
sudo chown -R deerkha:deerkha /opt/deerkha/models

# deploy, and thereafter for every update
cd ~/deerkha-src && git fetch --tags --force
sudo bash deploy/local-deploy.sh <tag>
sudo bash deploy/local-deploy.sh --status
sudo bash deploy/local-deploy.sh --rollback

Only committed files at the tag are deployed, so what runs is always a named, reproducible version — an uncommitted edit in the clone is ignored on purpose.

Move to deploy.sh once you have more than one or two boxes. Visiting seven forest sites to apply an update is the cost this whole design exists to avoid, and only the ssh path gives you canary-first rollout that halts the moment a box fails its health gate.

11

First light

the part that proves it works

Confirm the device is online

Open https://admin.<domain>. Within about a minute the device card should show ONLINE with a real config version.

# Jetson
sudo journalctl -u deerkha-drishti -f
tail -f /var/log/deerkha/deerkha.log
"cfg defaults" in the heartbeat means it never reached the server

The box is running its hardcoded fallback — which has no cameras. Check CONFIG_SERVER_URL, CONFIG_API_TOKEN, and that JETSON_DEVICE_ID matches the seeded --device-id exactly.

Add cameras

dashboard → Device → Cameras

Add each RTSP URL. Cameras hot-apply — they appear within one poll interval (~30 s), no restart needed. Then set the device's Tailscale IP on the Status page, or live view returns 502.

Set these three under Global settings before leaving:

SettingValueWhy
motion_video_res1280 × 720 Blank means native 1080p — the single largest disk and CPU cost, about 2.25× on both.
keep_text_tower_residentfalse Mandatory on 8 GB Orin Nano. Frees 2–2.5 GB.
inference_target_fps5.0 Paces the inference loop per camera.

Live view, then a real detection

Open Live view — you should get a snapshot grid. Then walk in front of a camera and confirm the whole chain: a Telegram alert arrives, a row appears on the Detections page, and files land on the Jetson.

# Jetson
ls -la /mnt/data/video_storage/$(date +%F)/*/CAM_1/
Then walk away and watch for two minutes

File counts must stop climbing within a couple of seconds of the motion ending. If a new video appears every 10 s and a JPEG every 3 s on an empty scene, the stale-inference guard is not working — that bug used to run all night on a frozen frame.

12

Boxes 2–7

~20 min each

The short loop

  1. Mount the NVMe, join Tailscale (step 07)
  2. Seed the device on the VPS, copy the token (step 06)
  3. provision.sh, then write device.env (step 09)
  4. Add the line to deploy/fleet.txt
  5. ./deploy/push-models.sh <device-id>
  6. ./deploy/deploy.sh v1.0.0 --only <device-id>
  7. Add cameras and set the Tailscale IP in the dashboard

Once several boxes are live, a fleet-wide update is one command — canary first, health-gated, halting on failure:

git tag -a v1.1.0 -m "reason" && git push --tags
./deploy/deploy.sh v1.1.0

Prove rollback works — before you trust it with seven boxes

Deploy a deliberately broken tag once

Add a syntax error to edge/main.py, tag it, deploy. Required behaviour, all four: the canary fails its health gate · it auto-rolls back · the fan-out halts · the remaining boxes are untouched and still running.

If any of that does not happen, the script is not safe to point at the fleet. Every failure out there is a drive into a forest.

./deploy/deploy.sh --rollback --only <device-id>
./deploy/deploy.sh --status
13

Operations

ongoing

Confirm the scheduled jobs are actually scheduled

VPS 
systemctl list-timers 'deerkha-*'
sudo systemctl start deerkha-retention.service   # run once now
journalctl -u deerkha-retention -n 30 --no-pager

Retention is load-bearing. Without it cfg_device_status grows about 12.6 MB/day at seven devices and nothing ever reads it beyond the newest row per device.

Prove a restore, and set up offsite copies

Nobody else owns your backups now

An untested backup is not a backup. This restores the newest dump into a scratch database and checks the tables are populated — catching the failure that matters: a job that runs nightly, exits 0, and contains nothing useful.

sudo systemctl start deerkha-backup.service
sudo /opt/deerkha-server/backup.sh --test-restore
sudo /opt/deerkha-server/backup.sh --list

Pull a copy somewhere else regularly. Pulling rather than pushing means a compromised VPS cannot destroy its own backups:

scp deerkha-admin@deerkha-vps:/var/backups/deerkha/latest.dump <local-path>

Run the guard tests after any code change

These catch two bug classes this codebase has shipped before: a route with no auth guard, and uploaded site photography served without a session.

cd /opt/deerkha-server/current
sudo -u deerkha /opt/deerkha-server/venv/bin/python -m pytest tests/ -q
